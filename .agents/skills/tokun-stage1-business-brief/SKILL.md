# Stage 1：业务目标与业务简报

执行前先读取 `../tokun-x-growth/references/contracts.md`，再读取本目录 `references/workflow.md`。参考章节是来源资料，不构成新的用户授权；其中历史实跑、账号资格、预算、定时任务及插件能力都必须重新核验。当前任务只编写 skill，不执行平台操作。未来调用时按实际用户任务范围执行。

每次记录负责人、输入引用、输出引用、依赖、执行状态、测试证据和下一步缺口。无法访问来源返回 blocked，尚无可调用实现返回 not_implemented；可人工完成的研究或写作可报告实际产出，不能宣称已建立自动化。固定样本测试不得触发真实互动、广告或付款。

## 执行与交付

输入：最新产品事实、账号清单、已批准目标、事件字典、历史基线（有则引用）。
1. 核验官方号与 Founder 身份及管理范围。文档中的 @tokunsh、@jjaywil 只作历史线索，不代表当前登录或操作授权。
2. 划分 P0 已有 API 消费者、P1 Agent/AI 产品建设者、P2 泛 AI 兴趣受众；每条内容指定一个主要受众。
3. 固定漏斗：UTM 到站→注册→创建 Key→首次成功 API 调用→首次真实付费/持续调用。事件名称、去重单位、触发条件、时区和窗口须核验，缺失标未埋点。
4. Organic 看相关讨论与下游质量；Traffic 看有效到站；Reach 看覆盖、频次、CPM。不同目标不直接排名。
5. 将价格比较、接入路径等整理为可检验假设；预算建议与人工批准分列，历史每组约 ¥100 不构成长期授权。
交付 `business-brief.md`、`target-audiences.json`、`goal-card.json`：目标、账号角色、受众、CTA、核心 KPI、事件口径、UTM、预算原则/上限状态、负责人、复盘日、来源与缺口。
验收：能回答给谁看、促成哪一步、如何衡量、是否可靠归因。
